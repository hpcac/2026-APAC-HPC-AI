# OpenFOAM DrivAer variant with Static Mesh Coarse case

## Task Workload and Input

Participants optimize the following workload.

- Application: [OpenFOAM](https://www.openfoam.com/) **v2512** (openfoam.com, December 2025 release)
- Case: [occDrivAerStaticMesh](https://develop.openfoam.com/committees/hpc/-/tree/develop/incompressible/simpleFoam/occDrivAerStaticMesh), 65 million cells
- Solver: `simpleFoam`
- Performance metric: the simpleFoam log line `Average wall-clock time per time step` (from the second step on). Lower is better.
- Node limit: **4 CPU nodes** on the chosen contest supercomputer (see Cluster Usage)
- Iterations: **40** (1 node), **80** (2 nodes), **150** (4 nodes)
- 1 / 2 / 4 node runs are for **scaling**. The scored run is the 4-node case.
- Reference: [OpenFOAM HPC Challenge 1 (OHC-1)](https://github.com/OpenFOAM-HPC-Challenge/OHC1)

The 65M mesh is the official coarse occDrivAerStaticMesh mesh ([Zenodo record 15012221](https://zenodo.org/records/15012221)). Do not change the mesh.

## Task Rules

- The scored run uses 4 standard CPU servers
  - For NCI Gadi users: Use **normalsr** queue (Intel Xeon Platinum 8470Q Sapphire Rapids)
  - For NSCC Singapore users: Use standard compute nodes (AMD EPYC 7713)
- Use OpenFOAM **v2512** from [openfoam.com](https://www.openfoam.com/). You may rebuild it (`WM_*`, compiler flags). Keep double precision. Do not patch the solver, and do not import code from other versions or forks.
- Follow the case [Allrun](https://develop.openfoam.com/committees/hpc/-/blob/develop/incompressible/simpleFoam/occDrivAerStaticMesh/Allrun). Use `fvSolution.fixedIter` and `controlDict.noWrite`. Set `endTime` to 40, 80, or 150 (1 / 2 / 4 nodes).
- Run the same commands Allrun runs, with the same flags: `decomposePar -constant` → `restore0Dir -processor` → `renumberMesh -constant -overwrite -parallel` → `potentialFoam -initialiseUBCs -parallel` → `applyBoundaryLayer -ybl 0.0450244 -parallel` → `simpleFoam -parallel`. Do not skip `potentialFoam` or `applyBoundaryLayer`. Do not change `-ybl`.
- Keep the mesh, `simpleFoam`, `fvSchemes`, and `fvSolution` unchanged.

## Optimization Guidelines

### Allowed Optimizations (including but not limited to)

- Decomposition (try this first): method, number of MPI ranks, and the settings for that method. Compiler flags and MPI tuning will not fix a bad decomposition.
- Mesh renumbering: Use of official v2512 `renumberMesh`
- Parallel strategies: MPI configuration, process placement and affinity
- Communication optimization: Reducing communication overhead and latency
- Compiler optimizations: Rebuild of official v2512, including `WM_*`, compilers, and optimization flags
- Memory management: Memory allocation and data locality via official v2512 runtime (environment variables and optimisation switches), not by changing sources
- System-level tuning: NUMA topology optimization, file system and storage access

### Prohibited Modifications

- Algorithm alteration: Patching solver or `renumberMesh` sources, or importing code from other OpenFOAM versions, branches, or forks
- Precision reduction: Lowering floating-point precision (including a single-precision `WM_SP` build), or reducing the numerical work per time step
- Input modification: Changing the 65M mesh, `simpleFoam`, `fvSchemes`, `fvSolution`, or `caseDefinition` physics
- Preparation chain: Skipping `potentialFoam` or `applyBoundaryLayer`, or changing Allrun’s `-ybl 0.0450244`

## Submission Guidelines

### Required content

Judges must be able to read, in **text**:

1. How you **decomposed** the mesh (`decomposePar` method, rank count, coefficients of that method)
2. The rest of the **preparation chain** and simpleFoam, with Allrun’s switches (scripts and/or text logs for `restore0Dir`, `renumberMesh`, `potentialFoam -initialiseUBCs`, `applyBoundaryLayer -ybl 0.0450244`, `simpleFoam`)
3. Which v2512 you ran: the site module, or how you rebuilt (`WM_*`, `wmake`, compiler flags) if you rebuilt
4. The **4-node** simpleFoam log that contains `Average wall-clock time per time step`, and `coefficient.dat` from that run
5. **1 / 2 / 4** node logs or plots for scaling
6. The OpenFOAM input files you used, as text (`decomposeParDict`, `controlDict`, `caseDefinition`)
7. **Presentation slides** for the interview

Do not submit binary files (the mesh, `processor*` directories, solver binaries, or a full install tree). Submit ASCII text files.

MPI profiling and analysis are strongly recommended.

### F1. Basic (vanilla)

Source and build:

- Official openfoam.com v2512, **unmodified**. Use the site `OpenFOAM/2512` module on Gadi or ASPIRE-2A, or rebuild the same source tree.
- Compiler and build flags may be set through `wmake/rules/*` or through build environment variables such as `WM_*` and `FOAM_EXTRA_CXXFLAGS`. Submit the exact build script. Submit any `wmake/rules/*` change as a patch file.
- Keep IEEE double-precision arithmetic. `-ffast-math`, `-Ofast`, and other flags that relax IEEE floating-point semantics are Bonus work, not Basic.
- `WM_LABEL_SIZE=32` or `64` are both fine.

Case files. You may edit only these:

- `system/include/caseDefinition`: `nCores`, `decompositionMethod` (`hierarchical` or `scotch`), `nHierarchical`.
- The coefficients of the chosen method (`hierarchicalCoeffs` or `scotchCoeffs`).
- `endTime` 40 / 80 / 150, as in Task Rules.

Everything else in the case stays as shipped: the mesh, `fvSchemes`, `fvSolution.fixedIter`, `controlDict.noWrite` including its function objects, and the physics in `caseDefinition`. Function objects stay in every tier, including Bonus: they are part of the work the task defines. If one is truly not needed, the organisers will remove it from the case for every team and announce it. Redirecting the solver's standard output to a file is fine.

Preparation chain:

- Run the Allrun commands with Allrun's switches, as in Task Rules. `renumberMesh -constant -overwrite -parallel` runs exactly as written, with its default method. Adding `-dict`, `-renumber-method`, or `-renumber-coeffs` is Bonus work.
- You may split the chain across separate jobs (for example, a small serial job for `decomposePar`, then the parallel steps). Every step must still run.

Runtime. All of these are Basic:

- Job scripts (Slurm or PBS), node and rank placement, affinity, SMT on or off.
- MPI and UCX parameters, and runtime environment variables.
- OpenFOAM runtime switches that do not change source code (for example `OptimisationSwitches`).
- Parallel I/O and file-system options on the command line, such as `-fileHandler`, `-hostRoots`, `-ioRanks` with node-local storage.

Reference baselines. Organiser vanilla results (full-rank `hierarchical` and `scotch`; Average and Cd at 40 / 80 / 150) are in `4.2 OpenFOAM Application Notes - Gadi`.

### F2. Bonus: experimental work

Anything Basic does not allow and the Prohibited tier does not forbid is experimental work. Examples:

- Other decomposition methods, built into v2512 or from its ThirdParty tree (for example `kahip`, `metis`, `ptscotch`, `multiLevel`, `simple`, `structured`). You may build a method's third-party library yourself and use a self-built official v2512 for `decomposePar` only.
- `method manual` decomposition or renumbering produced by your own program. Submit the program's source as text.
- Other renumbering methods or options (`-dict`, `-renumber-method`, `blockSize`, `zoltan` built against a library you supply).
- Changes to v2512 source: compiler pragmas and intrinsics, data layout, communication code such as `Pstream`, solver internals.
- Code brought in from other OpenFOAM versions, branches, or forks. State where each piece came from.
- Code replacement or injection without editing the tree: `LD_PRELOAD`, `-Wl,--wrap=`, compiler plug-ins or passes (for example LLVM-based transformations).
- Value-unsafe floating-point flags (F1).
- `fvSolution` settings that move work between MPI ranks without changing it, such as the GAMG `processorAgglomerator` entry. Other `fvSolution` changes (tolerances, `maxIter`, smoothers, `nCellsInCoarsestLevel`, relaxation factors) change the work per step and are Prohibited. `fvSchemes` stays unchanged in every tier.

Rules for Bonus work:

1. Submit your Basic result first. Bonus work does not replace it.
2. Prove the change is the same math, using F3.
3. Measure the speedup against your own Basic result on the same machine.
4. Show exactly what changed, as text.

A change that only swaps the decomposition method (unmodified source, all other files as in Basic) needs no extra baseline. Its Cd is checked with the "Sanity check" section, the same way as Basic.

### F3. Self-proof for Bonus changes

Build your own **pre-change baseline**: the same configuration as your Bonus run (same decomposition method and coefficients, same rank count, same node count), with the change removed.

- Compare Cd from `coefficient.dat` at the end of each of your 1-node (40 steps), 2-node (80 steps), and 4-node (150 steps) runs. These are three separate runs, the same as the Sanity check table. Each is compared with its own baseline at the same node count.
- If `coefficient.dat` is bit-identical to the baseline, the check passes.
- Otherwise, each of the three Cd values must be within ±0.5% of its baseline.
- A change that drifts outside the band during the 40 / 80 / 150 steps is a different computation, even if a much longer run would end at the same answer. You may present it as exploration. It does not count as "the same math, faster".

### F4. Prohibited in every tier

In addition to "Prohibited Modifications" above:

- Lower floating-point precision in any form, in Bonus too: `WM_SP`, `WM_SPDP`, mixed precision.
- Changing `fvSchemes`, and the `fvSolution` changes listed in F2 as Prohibited.
- Producing Cd, residuals, or timings by any means other than running the computation (for example, writing expected values).
- GPU acceleration. This is a CPU-only task.

### F5. Short answers

These apply to every team.

- **Is SMT allowed?** Yes.
- **Which files may I change for Basic?** See F1. Job scripts, MPI/UCX settings, and runtime environment variables are free. Case files: only the ones listed in F1.
- **Can I add `-dict` to `renumberMesh`?** Not in Basic. Yes in Bonus.
- **Can I patch `Pstream`, add pragmas, or use `LD_PRELOAD` / `--wrap`?** Not in Basic. Yes in Bonus, with F3.
- **Can I remove function objects or reduce log output?** No, in any tier. Redirecting standard output to a file is fine. See F1.
- **My method's third-party library is missing from the site module. Can I build it?** Yes, as Bonus work (F2).
- **Is the Cd check one 150-step run, or three runs?** Three runs: 1 node / 40 steps, 2 nodes / 80 steps, 4 nodes / 150 steps.
- **ASPIRE-2A multi-node timings vary a lot from run to run. How is that scored?** There is no noise correction in the score. The organisers' re-run is the reference number. In your submission and interview, show a few representative 4-node runs of your final configuration, with job IDs; you choose which. Showing your best run is fine. You may also add a separate noise showcase, picking runs that varied a lot, to show how the machine behaved. You may report unusual machine behaviour to help@nscc.sg.
