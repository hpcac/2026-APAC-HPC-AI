# OpenFOAM DrivAer variant with Static Mesh Coarse case

## Task Workload and Input

Participants optimize the following workload.

- Application: [OpenFOAM](https://www.openfoam.com/) **v2512** (openfoam.com, December 2025 release)
- Case: [occDrivAerStaticMesh](https://develop.openfoam.com/committees/hpc/-/tree/develop/incompressible/simpleFoam/occDrivAerStaticMesh), 65 million cells
- Solver: `simpleFoam`
- Performance metric: the simpleFoam log line `Average wall-clock time per time step` (from the second step on). Lower is better.
- Node limit: **4 CPU nodes** on the chosen contest supercomputer (see Cluster Usage)
- Iterations: **40** (1 node), **80** (2 nodes), **150** (4 nodes)
- 1 / 2 / 4 node runs are for **scaling**. The scored run is the 4-node case.
- Reference: [OpenFOAM HPC Challenge 1 (OHC-1)](https://github.com/OpenFOAM-HPC-Challenge/OHC1)

The 65M mesh is the official coarse occDrivAerStaticMesh mesh ([Zenodo record 15012221](https://zenodo.org/records/15012221)). Do not change the mesh.

## Task Rules

- The scored run uses 4 standard CPU servers
  - For NCI Gadi users: Use **normalsr** queue (Intel Xeon Platinum 8470Q Sapphire Rapids)
  - For NSCC Singapore users: Use standard compute nodes (AMD EPYC 7713)
- Use OpenFOAM **v2512** from [openfoam.com](https://www.openfoam.com/). You may rebuild it (`WM_*`, compiler flags). Keep double precision. Do not patch the solver, and do not import code from other versions or forks.
- Follow the case [Allrun](https://develop.openfoam.com/committees/hpc/-/blob/develop/incompressible/simpleFoam/occDrivAerStaticMesh/Allrun). Use `fvSolution.fixedIter` and `controlDict.noWrite`. Set `endTime` to 40, 80, or 150 (1 / 2 / 4 nodes).
- Run the same commands Allrun runs, with the same flags: `decomposePar -constant` → `restore0Dir -processor` → `renumberMesh -constant -overwrite -parallel` → `potentialFoam -initialiseUBCs -parallel` → `applyBoundaryLayer -ybl 0.0450244 -parallel` → `simpleFoam -parallel`. Do not skip `potentialFoam` or `applyBoundaryLayer`. Do not change `-ybl`.
- Keep the mesh, `simpleFoam`, `fvSchemes`, and `fvSolution` unchanged.

## General Rules

### Cluster Usage

This HPC task must be optimized on either **NCI Gadi** or **NSCC Singapore ASPIRE-2A**. Teams choose which supercomputer to use. Work on other machines may be shown as extra information; it is not the scored run.

If one contest supercomputer is down for maintenance, teams may switch to the other.

The scored run uses **4 CPU nodes**. Site-provided v2512 modules are the recommended starting point. Rebuilding the same v2512 tree is allowed. The rules do not require filling every core or thread on a node.

### Evaluation Criteria

Submissions are assessed on optimization method, technical understanding, and innovation, primarily through the team presentation.

### Performance Assessment

The absolute performance metrics of Gadi and ASPIRE-2A will not be directly compared. These metrics indicate the effectiveness of the optimization and are a significant factor in scoring. They are not the only criteria for ranking teams.

## Optimization Guidelines

### Allowed Optimizations (including but not limited to)

- Decomposition (try this first): method, number of MPI ranks, and the settings for that method. Compiler flags and MPI tuning will not fix a bad decomposition.
- Mesh renumbering: Use of official v2512 `renumberMesh`
- Parallel strategies: MPI configuration, process placement and affinity
- Communication optimization: Reducing communication overhead and latency
- Compiler optimizations: Rebuild of official v2512, including `WM_*`, compilers, and optimization flags
- Memory management: Memory allocation and data locality via official v2512 runtime (environment variables and optimisation switches), not by changing sources
- System-level tuning: NUMA topology optimization, file system and storage access

### Prohibited Modifications

- Algorithm alteration: Patching solver or `renumberMesh` sources, or importing code from other OpenFOAM versions, branches, or forks
- Precision reduction: Lowering floating-point precision (including a single-precision `WM_SP` build), or reducing the numerical work per time step
- Input modification: Changing the 65M mesh, `simpleFoam`, `fvSchemes`, `fvSolution`, or `caseDefinition` physics
- Preparation chain: Skipping `potentialFoam` or `applyBoundaryLayer`, or changing Allrun’s `-ybl 0.0450244`

## Submission Guidelines

### Required content

Judges must be able to read, in **text**:

1. How you **decomposed** the mesh (`decomposePar` method, rank count, coefficients of that method)
2. The rest of the **preparation chain** and simpleFoam, with Allrun’s switches (scripts and/or text logs for `restore0Dir`, `renumberMesh`, `potentialFoam -initialiseUBCs`, `applyBoundaryLayer -ybl 0.0450244`, `simpleFoam`)
3. Which v2512 you ran: the site module, or how you rebuilt (`WM_*`, `wmake`, compiler flags) if you rebuilt
4. The **4-node** simpleFoam log that contains `Average wall-clock time per time step`, and `coefficient.dat` from that run
5. **1 / 2 / 4** node logs or plots for scaling
6. The OpenFOAM input files you used, as text (`decomposeParDict`, `controlDict`, `caseDefinition`)
7. **Presentation slides** for the interview

Do not submit binary files (the mesh, `processor*` directories, solver binaries, or a full install tree). Submit ASCII text files.

MPI profiling and analysis are strongly recommended.

## Presentation Guidelines

- Duration: **15–20 minutes** presentation plus **10 minutes** of Q&A.
- Each team has **one** interview covering **both** the Qwen AI task and this OpenFOAM task. Teams choose the order and how much time to spend on each.
- Judges give **two** presentation scores from that interview: one for Qwen (60% of the AI task) and one for OpenFOAM (60% of the HPC task).
- Explain the optimization method, what improved, and the technical reasoning. Show 1 / 2 / 4 scaling. Do not treat Iris times as contest scores.
- Technical depth: Demonstrate understanding of both bottleneck identification and optimization strategies
- Performance analysis: Show before/after comparisons with detailed metrics
- Innovation highlight: Emphasize optimization approaches and their effectiveness

### Scoring

The OpenFOAM task score is **60%** presentation (method, technical understanding, innovation) and **40%** performance.

The 40% component is the 4-node performance metric. Lower is better. 1-node and 2-node results are a reference for the optimization and a clue for reproducing the 4-node result.

## Recommendations

- **Iris** is a practice cluster. Gadi and ASPIRE-2A are the contest supercomputers, and their hours are limited. On Iris, run the case until you know what each Allrun step does, and until you have an optimization idea to test. Then use Gadi or ASPIRE-2A hours on that idea. Do not use National Supercomputer hours to learn the case or to debug a first failed run. See [4.1 OpenFOAM Application Notes - Iris.md](4.1%20OpenFOAM%20Application%20Notes%20-%20Iris.md).
- Profile communication on the 4-node scored configuration before chasing further flags.
- Plan your Gadi or ASPIRE-2A hours before you submit. A 4-node run is expensive; count how many attempts your allocation can pay for. Do not sweep a large parameter grid on the contest supercomputers.
- Focus on hotspots: Concentrate on the most time-consuming parts of the 4-node run.
- Systematic approach: Write down each attempt and its result.

### Presentation Excellence

- Present a logical workflow: Tell the optimization as a problem-solving path, not a list of flags.
- Quantify impact: Show before/after of the 4-node performance metric. Use 1 / 2 / 4 node results as scaling evidence.
- Show understanding: Explain the bottleneck and why the change helped, not only the final 4-node number.
