# Qwen3-235B PD Application Notes: Firmus AI Cloud

This is a beginner-level worked example, not a template you need to adopt. Its main job is to save you cluster time: run the smoke tests below first, see what a healthy prefill/decode/router/aiperf log actually looks like, and get familiar with what's what before you start experimenting for real. It assumes your own cluster access, your own job-submission tooling, and your own copies of the sbatch scripts.

You are not required to use enroot/pyxis containers or SGLang, the choices this walkthrough happens to demonstrate. A self-built environment on shared storage is equally valid, and so is any other serving stack (vLLM, TensorRT-LLM, or either combined with Dynamo). The Task Rules do not restrict this at all. See `reference-scripts/` alongside this document for a fuller set of worked examples, and its `README.md` for what each one demonstrates.

Every `python3 -m sglang...` command below runs inside the `sglang-harbor.sqsh` container, as an `srun` step in your sbatch script, the same way Step 1 does it. Don't run these interactively (e.g. `srun --pty`): an interactive session keeps your GPU allocation, and burns cluster time, for as long as it stays open. Cluster time matters beyond your own runs, too. Most Slurm schedulers lower a user's scheduling priority the more time they've recently used, so idle or aimless trial-and-error can push your own later, real submissions further back in the queue. Run the smoke tests cheaply first, then experiment with intent.

## Container Images

Two enroot/pyxis container images are required for this task:

- `/scratch/enroot-images/sglang-harbor.sqsh`: the SGLang inference server image
- `/scratch/enroot-images/aiperf.sqsh`: the AIPerf benchmarking client image

Both images are referenced by absolute path inside the sbatch scripts via `--container-image=`, and are mounted read-only by enroot/pyxis at job launch. No manual `enroot import` or `enroot create` step is needed as long as these `.sqsh` files already exist at the paths above. The sbatch scripts consume them directly.

The model weights themselves are staged separately on shared storage, e.g. `/scratch/models/Qwen3-235B-A22B-Instruct-2507-FP8`, and are mounted into the container alongside `/scratch` (see the PD deployment section below).

## Smoke-Testing Your Container Setup

Before attempting a full PD deployment, verify the container image and GPU stack in three escalating steps. Each step is a single `sbatch` submission on your own cluster. A passing job is judged purely by its Slurm exit code (0 = pass), matching the harness convention of "the job's exit code is the verdict."

### Step 1: Container starts, GPU visible, SGLang importable

This is the minimal sanity check: the enroot image starts, the allocated GPU is visible inside the container, and the `sglang` Python package imports cleanly. A minimal single-GPU, single-node sbatch script performs the equivalent of:

```bash
srun --container-image=/scratch/enroot-images/sglang-harbor.sqsh \
  --container-mounts="/scratch:/scratch,<local-home-dir>:${HOME}" \
  bash -c '
    nvidia-smi -L
    python3 -c "import sglang; print(\"sglang\", getattr(sglang, \"__version__\", \"imported\"))"
  '
```

Key points:
- `--container-mounts` binds `/scratch` (where the images and model weights live) and a writable local directory as `$HOME` inside the container, since the container filesystem itself is otherwise read-only/ephemeral.
- `--gres=gpu:1` (or your Slurm-equivalent GPU request) is required so `nvidia-smi -L` reports a visible device.
- Submit with `sbatch 01-smoke-image.sbatch` (see `reference-scripts/`, and adjust the filename to your own copy of the script) and check the exit code in the job's log once it completes.

### Step 2: Single-instance serve

Once the image smoke test passes, bring up a single non-disaggregated SGLang server instance (for example with a small model) and confirm it becomes healthy. See `reference-scripts/02-smoke-serve.sbatch` for the full `srun --container-image=...` invocation; the command running inside the container is:

```bash
python3 -m sglang.launch_server \
  --model-path <model-path> --served-model-name qwen --trust-remote-code \
  --host 0.0.0.0 --port <port>
```

Poll the server's `/health` endpoint in a loop with a bounded timeout until it returns success, then shut the server down. This validates that model loading, weight sharding (if any), and the HTTP serving path all work end-to-end before you introduce PD disaggregation complexity.

### Step 3: Serve + AIPerf round trip

Finally, with the single instance from Step 2 still serving, run a short `aiperf profile` request against it from the `aiperf.sqsh` container to confirm the client can reach the server and complete a full request/response cycle (see `reference-scripts/03-smoke-serve-aiperf.sbatch`). A clean `aiperf` exit code (0) at this stage means your client, network path, and server are all correctly wired before moving on to the full PD topology.

Only after all three smoke steps pass should you proceed to the PD deployment below.

## PD Deployment Walkthrough

This section walks through a concrete, verified two-node PD split: **4× Prefill workers at TP=2** on one node, and **2× Decode workers at TP=4 (with `--ep-size 4`)** on the second node, an 8+8 GPU topology. All flag names and values below are copied verbatim from the working `reference-scripts/07-pd-235b-8plus8.sbatch` script. Do not alter them. Two other verified 235B splits (`08-pd-235b-12plus4-dynamo-match.sbatch` and `09-pd-235b-fatp-peak-bench.sbatch`) are available in the same folder as alternative starting points.

Node roles (2 nodes, 8 GPUs each):
- **Node 0 (head)**: 4 prefill workers, each `--tp-size 2` (2 GPUs per worker)
- **Node 1 (tail)**: 2 decode workers, each `--tp-size 4 --ep-size 4` (4 GPUs per worker)

### Common worker flags

Every worker (prefill and decode) is launched with `python3 -m sglang.launch_server` and shares this base flag set:

```bash
python3 -m sglang.launch_server \
  --model-path "$model" --served-model-name qwen --trust-remote-code \
  --context-length 8192 --tp-size "$tp" --mem-fraction-static 0.90 \
  --disaggregation-mode "$role" --disaggregation-transfer-backend nixl \
  "$@" --host 0.0.0.0 --port "$port"
```

- `--context-length 8192`
- `--mem-fraction-static 0.90`
- `--disaggregation-mode` is set to `prefill` or `decode` per worker
- `--disaggregation-transfer-backend nixl`: the transfer backend used for all workers

These are simplified for readability. The real script also detects each node's active InfiniBand device and exports it as `UCX_NET_DEVICES` before launch, since NIXL needs the right device for cross-node KV transfer and the two nodes can differ. Use `reference-scripts/07-pd-235b-8plus8.sbatch` (its `worker.sh` heredoc) as the actual command; treat the flags above as a summary, not something to copy-paste directly.

### Prefill workers (node 0, 4× TP=2)

Each prefill worker additionally takes a unique port and a unique `--disaggregation-bootstrap-port`:

| Worker | Port | `--disaggregation-bootstrap-port` |
|---|---|---|
| prefill-0 | 30100 | 9000 |
| prefill-1 | 30101 | 9001 |
| prefill-2 | 30102 | 9002 |
| prefill-3 | 30103 | 9003 |

Example launch for one prefill worker (2 GPUs, `--tp-size 2`):

```bash
python3 -m sglang.launch_server \
  --model-path "$model" --served-model-name qwen --trust-remote-code \
  --context-length 8192 --tp-size 2 --mem-fraction-static 0.90 \
  --disaggregation-mode prefill --disaggregation-transfer-backend nixl \
  --disaggregation-bootstrap-port 9000 --host 0.0.0.0 --port 30100
```

Repeat with the port/bootstrap-port pairs above for the remaining three prefill workers, each bound to 2 GPUs on node 0.

### Decode workers (node 1, 2× TP=4)

Decode workers add `--ep-size 4` and `--max-running-requests 256`, and use a separate port range:

| Worker | Port |
|---|---|
| decode-0 | 30200 |
| decode-1 | 30201 |

Example launch for one decode worker (4 GPUs, `--tp-size 4`):

```bash
python3 -m sglang.launch_server \
  --model-path "$model" --served-model-name qwen --trust-remote-code \
  --context-length 8192 --tp-size 4 --mem-fraction-static 0.90 \
  --disaggregation-mode decode --disaggregation-transfer-backend nixl \
  --ep-size 4 --max-running-requests 256 --host 0.0.0.0 --port 30200
```

Repeat for decode-1 on port 30201, on the same node.

### Router

Once all 6 workers (4 prefill + 2 decode) report healthy, start the PD router on node 0, pointing it at every worker's `http://<node-ip>:<port>` address. Prefill entries also take their bootstrap port as a second argument:

```bash
python3 -m sglang_router.launch_router --pd-disaggregation \
  --prefill "http://<head-ip>:30100" 9000 \
  --prefill "http://<head-ip>:30101" 9001 \
  --prefill "http://<head-ip>:30102" 9002 \
  --prefill "http://<head-ip>:30103" 9003 \
  --decode "http://<tail-ip>:30200" \
  --decode "http://<tail-ip>:30201" \
  --host 0.0.0.0 --port 8000
```

The router listens on port `8000` (`R_PORT` in the source script) and is the single endpoint that the benchmarking client talks to.

### Health checks

Before starting the router, poll each worker's `/health` endpoint (e.g. `http://<node-ip>:<port>/health`) in a retry loop with a bounded timeout, and only proceed once every worker responds successfully. After starting the router, poll the router's own `/health` endpoint the same way before sending any benchmark traffic. In the verified script, the health-check timeout budget is 600 seconds per endpoint, though servers typically become ready within a few minutes.

Bring workers up first (prefill workers, then decode workers), confirm all are healthy, then bring up the router last and confirm it is healthy before benchmarking.
