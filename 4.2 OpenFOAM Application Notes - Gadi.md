# OpenFOAM Application Notes: Gadi

These are the organisers' vanilla reference runs on **NCI Gadi**, and how to set yourself up there. The Task Rules ([Addendum F1](2.%20OpenFOAM%20HPC%20Task%20Rules.md#f1-basic-vanilla)) point here for the reference baselines.

Use these numbers to check your own Basic runs and to put a "before" next to your "after" in the slides. This is not an Allrun tutorial; for that, see [4.1 OpenFOAM Application Notes - Iris.md](4.1%20OpenFOAM%20Application%20Notes%20-%20Iris.md).

## Setting up on Gadi

### Disk

Check your project's space first:

```bash
lquota
```

Work in `/scratch/<project>/<user>/`. Home is 10 GiB and too small for this case.

What one team needs on `/scratch`:

| Item | Size |
|---|---:|
| `polyMesh_65M.tar.gz` | 3.2 GB |
| Unpacked `polyMesh` | 7.0 GB |
| One run directory after the full chain (`processor*`, any node count) | about 10 GB |

So the mesh plus a 1 / 2 / 4-node set of runs is about 40 GB if you keep every `processor*` tree. Delete `processor*` when a run is finished. Keep the text logs, `postProcessing/forceCoeffsAll/0/coefficient.dat`, and your dictionaries; that is what you submit.

If `lquota` shows your project cannot hold this, ask NCI for more scratch before you start (help@nci.org.au), not after a job fails on a full disk.

### Getting the mesh

A copy of the official Zenodo tarball is on Gadi for every user:

```
/scratch/public/pz7344/apac2026-openfoam/polyMesh_65M.tar.gz
/scratch/public/pz7344/apac2026-openfoam/polyMesh_65M.tar.gz.md5
```

Copy it into your own scratch, check it, and unpack it there:

```bash
mkdir -p /scratch/<project>/<user>/occDrivAer
cd /scratch/<project>/<user>/occDrivAer
cp /scratch/public/pz7344/apac2026-openfoam/polyMesh_65M.tar.gz* .
md5sum -c polyMesh_65M.tar.gz.md5      # polyMesh_65M.tar.gz: OK
tar -xzf polyMesh_65M.tar.gz           # gives polyMesh/
```

Do this on a login node. It costs no SU.

`/scratch/public` deletes files two weeks after they are placed there, without warning. This copy was placed on 2026-10-06 and expires around 2026-10-20; the organisers will place it again before then. **Do not symlink or point your case at `/scratch/public`.** If the file is removed while your job is reading it, the job breaks. Always run from your own copy.

If the public copy is not there, download from Zenodo on a login node and check the same md5:

```bash
wget -O polyMesh_65M.tar.gz "https://zenodo.org/records/15012221/files/polyMesh_65M.tar.gz?download=1"
echo "50393a15d84f53255fda85ac702390e9  polyMesh_65M.tar.gz" | md5sum -c
```

The unpacked mesh has 65 334 765 cells (`grep -a nCells polyMesh/owner`).

### Sharing within a team

Keep one team directory that everyone in your project group can write to, so you do not each hold a 7 GB mesh:

```bash
mkdir -p /scratch/<project>/<team>
chmod 2770 /scratch/<project>/<team>    # group read/write, new files keep the group
```

Each run still needs its own case directory. Many runs can link the same unpacked `polyMesh` read-only (`ln -s /scratch/<project>/<team>/polyMesh constant/polyMesh`); `decomposePar -constant` only reads it.

### Before the first 4-node run

Run one short 1-node job first (`endTime 3`, full Allrun chain). On Gadi it took 6.5 minutes and 22.6 SU, and it shows that the module, the mesh path, the PBS script and the logs are right. Then run 1 / 2 / 4 nodes. A 4-node run that fails near the end costs about 200 SU.

## How the reference runs were made

| | |
|---|---|
| Queue | `normalsr` (Intel Xeon Platinum 8470Q, 104 cores and 512 GiB per node) |
| OpenFOAM | site module `OpenFOAM/2512` (loads `openmpi/4.1.7`); logs show `Build : _87ed40d256-20251219 OPENFOAM=2512 version=v2512` |
| Case | official [occDrivAerStaticMesh](https://develop.openfoam.com/committees/hpc/-/tree/develop/incompressible/simpleFoam/occDrivAerStaticMesh) at commit `84c26243`, unmodified `Allrun`, `fvSolution.fixedIter`, `controlDict.noWrite` |
| Mesh | Zenodo 15012221 `polyMesh_65M.tar.gz` |
| Ranks | full nodes: 104 / 208 / 416 MPI ranks, no extra `mpirun` options |
| `endTime` | 40 / 80 / 150 on 1 / 2 / 4 nodes |
| Changed | only `system/include/caseDefinition`: `nCores`, `decompositionMethod`, and `nHierarchical` for `hierarchical` |

Decomposition:

- `hierarchical`: `nHierarchical` `(13 4 2)` / `(13 8 2)` / `(13 8 4)`. These are simple factorisations of the rank count, not tuned.
- `scotch`: no `scotchCoeffs`, so Scotch's own defaults. The shipped `nHierarchical (16 8 4)` is still in those `caseDefinition` files; `scotch` does not read it.

The whole chain ran in one PBS job per run, with the resources below. Only the node count, `ncpus` and `mem` change between 1, 2 and 4 nodes.

```bash
#PBS -q normalsr
#PBS -l ncpus=416
#PBS -l mem=1664GB
#PBS -l walltime=01:00:00
#PBS -l storage=scratch/<project>
#PBS -l wd

module load OpenFOAM/2512
bash Allrun      # Allrun's own shebang is "bash -l", which drops the loaded module inside PBS
```

## Reference results

| Decomposition | Nodes | MPI ranks | Steps | Average (s/step) | Cd | Job walltime | SU |
|---|---:|---:|---:|---:|---:|---:|---:|
| `hierarchical` | 1 | 104 | 40 | 8.605 | 0.439932 | 00:12:08 | 42.06 |
| `hierarchical` | 2 | 208 | 80 | 4.249 | 0.335041 | 00:12:20 | 85.51 |
| `hierarchical` | 4 | 416 | 150 | 2.380 | 0.289985 | 00:13:58 | 193.67 |
| `scotch` | 1 | 104 | 40 | 8.478 | 0.438060 | 00:13:15 | 45.93 |
| `scotch` | 2 | 208 | 80 | 4.213 | 0.339636 | 00:14:14 | 98.68 |
| `scotch` | 4 | 416 | 150 | 2.126 | 0.291876 | 00:16:20 | 226.49 |

Full-precision values are in the logs (see [Job IDs and logs](#job-ids-and-logs)).

On 4 nodes, default `scotch` is about 11% faster per step than this `hierarchical` split. That is the gap a decomposition alone can make, before any compiler or MPI tuning.

The contest quantity is **Average**: the `Average wall-clock time per time step` line near the end of the simpleFoam log, measured from the second step on. Lower is better. The scored run is the 4-node one.

Cd is the last line of `postProcessing/forceCoeffsAll/0/coefficient.dat`, column `Cd`. It is not in the simpleFoam log.

### What Cd tells you

- Cd depends on the decomposition. `hierarchical` and `scotch` differ from each other by about 0.4% at 40 steps, 1.4% at 80 steps and 0.7% at 150 steps. Neither is "the right one".
- With the same method, rank count and coefficients, repeat runs give nearly the same Cd. An earlier set of the same three `hierarchical` runs on Gadi (August 2026) matched the table to a relative 1e-13 at 1 node, 1e-7 at 2 nodes and 3e-6 at 4 nodes; its Average was 0.2–0.7% lower. If your Basic run uses exactly one of the configurations above and your Cd differs in the third or fourth digit, check your case files before you look anywhere else.
- For any other configuration, the "Sanity check" table in the Task Rules is the check. It is a sanity check, not a pass/fail gate, and there is no official ±% band for Basic (Addendum F0).

## What one run costs

Three different times appear on Gadi. Do not mix them up.

| Time | Where you find it | What it is |
|---|---|---|
| Average | simpleFoam log, `Average wall-clock time per time step = …` | Seconds per solver step. The contest quantity. |
| simpleFoam time | `real` printed after `simpleFoam` in the job's `.o` file | The whole `simpleFoam -parallel` process: first step, compiling the coded function object, every step, finishing. About 6–7 minutes here at every node count. **Not** the contest quantity. |
| Job walltime and SU | `Resource Usage` block at the end of the job's `.o` file: `Walltime Used`, `Service Units` | What you are billed. `normalsr` charges 2 SU per core-hour, so a full node is 208 SU per hour. |

Per step of the chain, in seconds (`real` from the job's `.o` file):

| Decomposition | Nodes | `decomposePar` | `renumberMesh` | `potentialFoam` | `applyBoundaryLayer` | `simpleFoam` | Job walltime | SU |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `hierarchical` | 1 | 172 | 40 | 61 | 40 | 402 | 00:12:08 | 42.06 |
| `hierarchical` | 2 | 200 | 47 | 50 | 40 | 394 | 00:12:20 | 85.51 |
| `hierarchical` | 4 | 270 | 58 | 48 | 39 | 408 | 00:13:58 | 193.67 |
| `scotch` | 1 | 248 | 39 | 61 | 41 | 398 | 00:13:15 | 45.93 |
| `scotch` | 2 | 318 | 46 | 50 | 39 | 391 | 00:14:14 | 98.68 |
| `scotch` | 4 | 458 | 51 | 44 | 40 | 370 | 00:16:20 | 226.49 |

Preparation (everything before `simpleFoam`) is 40–60% of the job walltime. It does not change Average, but you pay for it on every run.

`restore0Dir` is not timed by Allrun; it and module loading are the rest of the job walltime.

`decomposePar` is a single process, but the PBS job holds every requested core while it runs. On 4 nodes with `scotch` it took 7.6 minutes, which billed 106 SU for one busy core: more than `simpleFoam` itself (86 SU). Addendum F1 allows splitting the chain into separate jobs. We ran the 1-node `scotch` chain as a 16-core `decomposePar` + `restore0Dir` job (4.4 minutes, 2.35 SU) followed by a 104-core job for the remaining steps (9.2 minutes, 31.72 SU): 34.07 SU in total instead of 45.93, with the same decomposition (same cells on every rank) and the same Cd to 1e-14.

Budget for a full 1 / 2 / 4-node set, one job each: about 321 SU with `hierarchical` and 371 SU with `scotch`, plus whatever failed attempts you make.
