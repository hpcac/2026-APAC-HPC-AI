# OpenFOAM Application Notes: Gadi

These are the organisers' vanilla reference runs on **NCI Gadi**, and how to set yourself up there. The Task Rules ([Addendum F1](2.%20OpenFOAM%20HPC%20Task%20Rules.md#f1-basic-vanilla)) point here for the reference baselines.

This is not an Allrun tutorial; for that, see [4.1 OpenFOAM Application Notes - Iris.md](4.1%20OpenFOAM%20Application%20Notes%20-%20Iris.md).

## Setting up on Gadi

### Disk

Check your project's space first:

```bash
lquota
```

Work in `/scratch/<project>/<user>/`. Home is 10 GiB and too small for this case.

What one team needs on `/scratch`:

| Item | Size |
|---|---:|
| `polyMesh_65M.tar.gz` | 3.2 GB |
| Unpacked `polyMesh` | 7.0 GB |
| One run directory after the full chain (`processor*`, any node count) | about 10 GB |

So the mesh plus a 1 / 2 / 4-node set of runs is about 40 GB if you keep every `processor*` tree.

### Getting the mesh

A copy of the official Zenodo tarball is on Gadi for every user:

```
/scratch/public/pz7344/apac2026-openfoam/polyMesh_65M.tar.gz
/scratch/public/pz7344/apac2026-openfoam/polyMesh_65M.tar.gz.md5
```

Copy it into your own scratch, check it, and unpack it there:

```bash
mkdir -p /scratch/<project>/<user>/occDrivAer
cd /scratch/<project>/<user>/occDrivAer
cp /scratch/public/pz7344/apac2026-openfoam/polyMesh_65M.tar.gz* .
md5sum -c polyMesh_65M.tar.gz.md5      # polyMesh_65M.tar.gz: OK
tar -xzf polyMesh_65M.tar.gz           # gives polyMesh/
```

Do this on a login node. It costs no SU.

`/scratch/public` deletes files two weeks after they are placed there, without warning.

If the public copy is not there, download from Zenodo on a login node and check the same md5:

```bash
wget -O polyMesh_65M.tar.gz "https://zenodo.org/records/15012221/files/polyMesh_65M.tar.gz?download=1"
echo "50393a15d84f53255fda85ac702390e9  polyMesh_65M.tar.gz" | md5sum -c
```

The unpacked mesh has 65 334 765 cells (`grep -a nCells polyMesh/owner`).

Many case directories can link one unpacked `polyMesh` (`ln -s <path>/polyMesh constant/polyMesh`); `decomposePar -constant` only reads it. All the runs below did this.

## How the reference runs were made

| | |
|---|---|
| Queue | `normalsr` (Intel Xeon Platinum 8470Q, 104 cores and 512 GiB per node) |
| OpenFOAM | site module `OpenFOAM/2512` (loads `openmpi/4.1.7`); logs show `Build : _87ed40d256-20251219 OPENFOAM=2512 version=v2512` |
| Case | official [occDrivAerStaticMesh](https://develop.openfoam.com/committees/hpc/-/tree/develop/incompressible/simpleFoam/occDrivAerStaticMesh) at commit `84c26243`, unmodified `Allrun`, `fvSolution.fixedIter`, `controlDict.noWrite` |
| Mesh | Zenodo 15012221 `polyMesh_65M.tar.gz` |
| Ranks | full nodes: 104 / 208 / 416 MPI ranks, no extra `mpirun` options |
| `endTime` | 40 / 80 / 150 on 1 / 2 / 4 nodes |
| Changed | only `system/include/caseDefinition`: `nCores`, `decompositionMethod`, and `nHierarchical` for `hierarchical` |

Decomposition:

- `hierarchical`: `nHierarchical` `(13 4 2)` / `(13 8 2)` / `(13 8 4)`. These are simple factorisations of the rank count, not tuned.
- `scotch`: no `scotchCoeffs`, so Scotch's own defaults. The shipped `nHierarchical (16 8 4)` is still in those `caseDefinition` files; `scotch` does not read it.

The whole chain ran in one PBS job per run, with the resources below. Only the node count, `ncpus` and `mem` change between 1, 2 and 4 nodes.

```bash
#PBS -q normalsr
#PBS -l ncpus=416
#PBS -l mem=1664GB
#PBS -l walltime=01:00:00
#PBS -l storage=scratch/<project>
#PBS -l wd

module load OpenFOAM/2512
bash Allrun      # Allrun's own shebang is "bash -l", which drops the loaded module inside PBS
```

## Reference results

| Decomposition | Nodes | MPI ranks | Steps | Average (s/step) | Cd | Job walltime | SU |
|---|---:|---:|---:|---:|---:|---:|---:|
| `hierarchical` | 1 | 104 | 40 | 8.605 | 0.439932 | 00:12:08 | 42.06 |
| `hierarchical` | 2 | 208 | 80 | 4.249 | 0.335041 | 00:12:20 | 85.51 |
| `hierarchical` | 4 | 416 | 150 | 2.380 | 0.289985 | 00:13:58 | 193.67 |
| `scotch` | 1 | 104 | 40 | 8.478 | 0.438060 | 00:13:15 | 45.93 |
| `scotch` | 2 | 208 | 80 | 4.213 | 0.339636 | 00:14:14 | 98.68 |
| `scotch` | 4 | 416 | 150 | 2.126 | 0.291876 | 00:16:20 | 226.49 |

Full-precision values are in the logs (see [Job IDs and logs](#job-ids-and-logs)).

On 4 nodes, default `scotch` is about 11% faster per step than this `hierarchical` split.

The 4-node `scotch` Average includes two slow steps (steps 52 and 53: 4.31 s and 6.48 s; the other 147 steps took 2.05–2.60 s). Without them its mean is 2.082 s. The case's timing function prints a warning in that log because of them. The other five runs have no such steps.

The contest quantity is **Average**: the `Average wall-clock time per time step` line near the end of the simpleFoam log, measured from the second step on. Lower is better. The scored run is the 4-node one.

Cd is the last line of `postProcessing/forceCoeffsAll/0/coefficient.dat`, column `Cd`. It is not in the simpleFoam log.

### What Cd tells you

- Cd depends on the decomposition. `hierarchical` and `scotch` differ from each other by about 0.4% at 40 steps, 1.4% at 80 steps and 0.7% at 150 steps.
- With the same method, rank count and coefficients, repeat runs give nearly the same Cd. An earlier set of the same three `hierarchical` runs on Gadi matched the table to a relative 1e-13 at 1 node, 1e-7 at 2 nodes and 3e-6 at 4 nodes; its Average was 0.2–0.7% lower.
- How Cd is checked is in the Task Rules ("Sanity check", Addendum F0 and F3).

## What one run costs

Three different times appear on Gadi:

| Time | Where you find it | What it is |
|---|---|---|
| Average | simpleFoam log, `Average wall-clock time per time step = …` | Seconds per solver step. The contest quantity. |
| simpleFoam time | `real` printed after `simpleFoam` in the job's `.o` file | The whole `simpleFoam -parallel` process: first step, compiling the coded function object, every step, finishing. About 6–7 minutes here at every node count. **Not** the contest quantity. |
| Job walltime and SU | `Resource Usage` block at the end of the job's `.o` file: `Walltime Used`, `Service Units` | What you are billed. `normalsr` charges 2 SU per core-hour, so a full node is 208 SU per hour. |

Per step of the chain, in seconds (`real` from the job's `.o` file):

| Decomposition | Nodes | `decomposePar` | `renumberMesh` | `potentialFoam` | `applyBoundaryLayer` | `simpleFoam` | Job walltime | SU |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `hierarchical` | 1 | 172 | 40 | 61 | 40 | 402 | 00:12:08 | 42.06 |
| `hierarchical` | 2 | 200 | 47 | 50 | 40 | 394 | 00:12:20 | 85.51 |
| `hierarchical` | 4 | 270 | 58 | 48 | 39 | 408 | 00:13:58 | 193.67 |
| `scotch` | 1 | 248 | 39 | 61 | 41 | 398 | 00:13:15 | 45.93 |
| `scotch` | 2 | 318 | 46 | 50 | 39 | 391 | 00:14:14 | 98.68 |
| `scotch` | 4 | 458 | 51 | 44 | 40 | 370 | 00:16:20 | 226.49 |

Preparation (everything before `simpleFoam`) is 40–60% of the job walltime. It does not change Average, but you pay for it on every run.

`restore0Dir` is not timed by Allrun; it and module loading are the rest of the job walltime.

The table above is the plain Allrun, one PBS job per run: about 321 SU for a 1 / 2 / 4-node set with `hierarchical` and 371 SU with `scotch`.

## Splitting the chain into two jobs

`decomposePar` is a single process, but a one-job Allrun holds every requested core while it runs. On 4 nodes with `scotch` it took 7.6 minutes, which billed 106 SU for one busy core: more than `simpleFoam` itself (86 SU).

Addendum F1 allows splitting the chain across separate jobs, as long as every step still runs:

1. **Serial job**, small: `decomposePar -constant`, then `restore0Dir -processor`. 16 cores and 64 GB were enough on Gadi (`decomposePar` used 40–46 GB of memory for 104 to 416 subdomains).
2. **Parallel job**, full nodes, started only if the first one succeeded: `renumberMesh -constant -overwrite -parallel`, `potentialFoam -initialiseUBCs -parallel`, `applyBoundaryLayer -ybl 0.0450244 -parallel`, `simpleFoam -parallel`.

The serial job also does Allrun's setup (copying `controlDict.noWrite` to `controlDict` and `fvSolution.fixedIter` to `fvSolution`). The two jobs were chained with a PBS dependency:

```bash
a=$(qsub serial.pbs)                         # #PBS -l ncpus=16,mem=64GB
qsub -W depend=afterok:$a parallel.pbs       # #PBS -l ncpus=416,mem=1664GB
```

What it saved with `scotch` (same case, same mesh, same module):

| Nodes | One job | Serial job | Parallel job | Split total | Saved |
|---:|---:|---:|---:|---:|---:|
| 1 | 45.93 SU | 2.35 SU (00:04:24) | 31.72 SU (00:09:09) | 34.07 SU | 26% |
| 2 | 98.68 SU | 3.05 SU (00:05:43) | 61.36 SU (00:08:51) | 64.41 SU | 35% |
| 4 | 226.49 SU | 4.19 SU (00:07:51) | 114.63 SU (00:08:16) | 118.82 SU | 48% |

A full 1 / 2 / 4-node `scotch` set drops from 371 SU to 217 SU. The split runs gave the same Cd as the one-job runs to a relative 1e-14 at 1 node and 4e-7 at 2 and 4 nodes, the same spread as repeating a run. The saving grows with node count because the serial step gets longer and the idle cores more numerous; `hierarchical` decomposes faster, so it saves less, but the idea is the same.

Splitting changes SU and walltime, not Average.

## Reusing a decomposition, and shorter runs

The Iris example scripts linked from [4.1](4.1%20OpenFOAM%20Application%20Notes%20-%20Iris.md) already split the chain into cut, initialise and solve jobs, and rerun `simpleFoam` on one prepared decomposition (`LADDER.md`, "What you can reuse"). These are the same ideas measured on Gadi.

Rerunning only `simpleFoam` on the prepared `scotch` decomposition from the split runs above (`processor*` linked, not copied):

| Nodes | Steps | SU | Job walltime | Average (s/step) | Cd | Full chain, split: SU / Cd |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 40 | 23.92 | 00:06:54 | 8.442 | 0.43806006706835021 | 34.07 / 0.43806006706834949 |
| 4 | 150 | 91.29 | 00:06:35 | 2.088 | 0.29187622364314331 | 118.82 / 0.29187596691164680 |

- Cd matched the full chain to a relative 2e-15 at 1 node and 9e-7 at 4 nodes; the two full-chain 4-node `scotch` runs differ from each other by 4e-7.
- Average was within the spread of the full-chain runs.
- `controlDict.noWrite` writes no time directories, so the prepared `processor*` were unchanged afterwards and can be used again.
- These runs skip the preparation steps, so they are not a full chain.

Average from fewer steps. The simpleFoam log prints every step's wall-clock time, so a shorter run's Average can be read off the full runs. The mean of steps 2–21 (a 21-step run) against the full run's Average:

| | 1 node | 2 nodes | 4 nodes |
|---|---:|---:|---:|
| `hierarchical` | +0.1% | +0.2% | +1.9% |
| `scotch` | −0.1% | −0.3% | −1.9% |

At 4 nodes the first steps of the `hierarchical` run were slower than the rest, and the `scotch` full-run Average includes the two slow steps noted above. Cd after fewer steps is not comparable with the table.

A 3-step 1-node run of the full chain took 6.5 minutes and 22.6 SU.
