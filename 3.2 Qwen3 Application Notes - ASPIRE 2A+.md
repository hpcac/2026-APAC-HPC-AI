# Qwen3-235B PD Application Notes: NSCC ASPIRE 2A+

This is the ASPIRE 2A+ counterpart of [3.1 Qwen3 Application Notes - Firmus AI Cloud.md](3.1%20Qwen3%20Application%20Notes%20-%20Firmus%20AI%20Cloud.md). Like 3.1, it is a worked example, not a template you need to adopt: SGLang and containers are what it happens to demonstrate, and the Task Rules do not require either. Its job is to get your environment working on ASPIRE 2A+ cheaply, before you spend GPU hours on real experiments.

What is different from Firmus: the scheduler is PBS Pro, not Slurm, and containers are started through PBS's own enroot support, not pyxis. The SGLang worker flags in 3.1 carry over; its 8+8 topology does not fit on H100 (see [Fitting Qwen3-235B FP8 on H100](#fitting-qwen3-235b-fp8-on-h100)).

The complete job scripts for each step are in [3.2-aspire2p-scripts/](3.2-aspire2p-scripts/); the excerpts below show what matters in them.

Every job below is a batch job. Don't hold GPUs with an interactive job (`qsub -I`) while you think: you are charged for the whole time it is open. Run the smoke tests with a small model first, and keep exploratory runs short.

## PBS on ASPIRE 2A+

Submit to the routing queue `normal`. Jobs asking for 1–7 GPUs land in `aiq1`, 8 or more in `aiq2`. `qstat`, `qsub` and `qdel` are in `/opt/pbs/bin`.

Always give a project, memory and walltime. The server defaults are `walltime=00:05:00` and `mem=10mb`; a job that does not ask for memory gets 10 MB.

```bash
#PBS -q normal
#PBS -P <project-id>
#PBS -l walltime=00:10:00
#PBS -j oe

# one GPU
#PBS -l select=1:ncpus=14:ngpus=1:mem=235gb

# two full nodes, 16 GPUs
#PBS -l select=2:ncpus=112:ngpus=8:mpiprocs=1:mem=1880gb
```

Charging is per GPU: **1 GPU-hour = 128 SU**, CPU is not charged separately, and every GPU comes with 14 cores and 235 GB of memory whether you ask for them or not. You are charged for the walltime used, not the walltime requested (`myprojects -p <project-id>` shows the balance). A 2-node, 16-GPU job that runs 10 minutes costs 16 × 128 / 6 ≈ 341 SU.

Short walltimes help a job start sooner: the scheduler can fit it into the gap before a large job's nodes become free if it will finish in time. Ask for what the run needs, not the queue maximum.

## Containers with PBS and enroot

ASPIRE 2A+ has no pyxis. PBS creates the enroot container for you from a `.sqsh` before the job script starts, on every node of the job:

```bash
#PBS -l select=1:ncpus=14:ngpus=1:mem=235gb:container_engine=enroot
#PBS -l container_image=/absolute/path/to/image.sqsh
#PBS -l container_name=sglang

enroot start sglang python3 -m sglang.launch_server ...
```

- `container_engine=enroot` goes inside `select`. If you give it, you must also give `container_name`, or `qsub` rejects the job.
- `container_image` must be an absolute path (`$HOME` and `~` are accepted).
- The job script itself runs on the host. Only what you put after `enroot start <name>` runs in the container.
- Only the GPUs allocated to the job are visible inside the container.
- `/scratch` and your home directory are mounted in the container by default. The enroot data for the job lives on the node's local `/raid` and is removed with the job.

Multi-node jobs:

- `enroot start --env ...` and `--mount ...` only take effect on the first node. Put environment variables in a file and pass it with `#PBS -l enroot_env_file=<file>`; add mounts with `#PBS -l enroot_mounts="/src:/dst;/src2:/dst2"`.
- Fake root (`enroot start --root`) does not work across nodes.
- Three ways to start a process on another node of your job all worked: `ssh <node>` from inside the job, `pbsdsh`, and the system OpenMPI on the GPU nodes (`/usr/mpi/gcc/openmpi-4.1.7a1/bin/mpirun -hostfile $PBS_NODEFILE -map-by ppr:1:node ...`). With each of them, `enroot start` on the other node sees only that node's GPUs of your job.
- If you start a container over ssh, pass `PBS_JOBID` along (`ssh <node> "export PBS_JOBID=${PBS_JOBID}; enroot start ..."`): enroot finds the job's container through it.
- Node names in `$PBS_NODEFILE` are fully qualified (`a2ap-dgx035.asp2p.nscc.sg`); `CUDA_VISIBLE_DEVICES` in the job environment holds GPU UUIDs, not indices.
- From the login node, `export PBS_JOBID=<id>.pbs111` and then `ssh <node>` lets you look at a running job's node.

PBS takes one `container_image` per job. To use a second image in the same job (the AIPerf client next to the SGLang server, for example), create it yourself inside the job:

```bash
enroot create --name aiperf /path/to/aiperf-0.12.0.sqsh
enroot start aiperf "aiperf profile --model qwen ..."
```

**The AIPerf image takes its command as one string.** Its entrypoint is `bash -c "$@"`, so with `enroot start aiperf aiperf profile --model ...` only the first word runs: `aiperf` prints its help and exits 0, and nothing is measured. Quote the whole command line, as above. The SGLang image does not have this problem.

## Smoke-testing your container setup

The three steps of 3.1, as PBS jobs (`01-smoke-image.pbs`, `02-smoke-serve.pbs`, `03-smoke-serve-aiperf.pbs`). Each is a one-GPU job; the job's exit status is the verdict (`qstat -fx <id> | grep Exit_status`, 0 = pass). Submit from the directory where you want the `.o` file.

### Step 1: Container starts, GPU visible, SGLang importable

```bash

#PBS -N a2p-01-image
#PBS -q normal
#PBS -P <project-id>
#PBS -l select=1:ncpus=14:ngpus=1:mem=235gb:container_engine=enroot
#PBS -l container_image=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/qwen3/images/sglang-v0.5.17-cu129.sqsh
#PBS -l container_name=sglang
#PBS -l walltime=00:10:00
#PBS -j oe
set -euo pipefail

enroot start sglang bash -c 'set -euo pipefail
  nvidia-smi -L
  python3 -c "import sglang; print(\"sglang\", getattr(sglang, \"__version__\", \"imported\"))"
'
```

A passing `.o` file ends with:

```

sglang 0.5.17
```

### Step 2: Single-instance serve

Same PBS header. Start one non-disaggregated server with Qwen3-0.6B and wait for `/health`:

```bash
MODEL=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/qwen3/models/Qwen3-0.6B

enroot start --env MODEL="${MODEL}" sglang bash -c 'set -euo pipefail
  python3 -m sglang.launch_server --model-path "${MODEL}" \
    --host 127.0.0.1 --port 30000 --tp-size 1 --mem-fraction-static 0.4 \
    --context-length 4096 --trust-remote-code >&2 &
  timeout 300 curl -sf --retry-connrefused --retry-all-errors \
    --retry-delay 2 --retry 150 --max-time 2 \
    -o /dev/null http://127.0.0.1:30000/health
  echo "READY after ${SECONDS}s"
  kill %1
'
```

`--env` is fine here because it is a single node.

### Step 3: Serve + AIPerf round trip

The server runs in the PBS-created `sglang` container; the AIPerf container is created inside the job:

```bash
PUB=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/qwen3
MODEL=${PUB}/models/Qwen3-0.6B
ART=${PBS_O_WORKDIR}/aiperf-${PBS_JOBID%%.*}

enroot start sglang python3 -m sglang.launch_server \
  --model-path "${MODEL}" --served-model-name qwen \
  --host 0.0.0.0 --port 30000 --tp-size 1 --mem-fraction-static 0.4 \
  --context-length 4096 --trust-remote-code >&2 &
trap 'kill $! 2>/dev/null || true' EXIT

timeout 300 curl -sf --retry-connrefused --retry-all-errors \
  --retry-delay 2 --retry 150 --max-time 2 \
  -o /dev/null http://127.0.0.1:30000/health

enroot create --name aiperf ${PUB}/images/aiperf-0.12.0.sqsh
enroot start aiperf "aiperf profile \
  --model qwen --tokenizer ${MODEL} \
  --url http://127.0.0.1:30000 --endpoint-type chat --streaming \
  --request-count 2 --concurrency 1 --num-dataset-entries 2 \
  --synthetic-input-tokens-mean 16 --output-tokens-mean 8 \
  --artifact-dir ${ART}"
ls ${ART}/*.json
```

The last line makes the job fail if AIPerf measured nothing (see the entrypoint note above). A passing run prints the AIPerf metrics table (2 requests, input 16 and output 8 tokens) and writes `profile_export_aiperf.json` into `${ART}`.

Only after all three pass, move on to PD.

## PD across two nodes

The smallest PD deployment, as in `3.1-firmus-scripts/04` (here `04-pd-minimal-2node.pbs`): one prefill worker on one node, one decode worker on another, the router next to the prefill worker, and two AIPerf requests through the router. One GPU per node is enough; `place=scatter` keeps the two chunks on different nodes so the KV cache crosses InfiniBand.

```bash
#PBS -l select=2:ncpus=14:ngpus=1:mpiprocs=1:mem=235gb:container_engine=enroot
#PBS -l place=scatter
#PBS -l container_image=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/qwen3/images/sglang-v0.5.17-cu129.sqsh
#PBS -l container_name=sglang
```

PBS creates the `sglang` container on both nodes. Each worker is started on its node over ssh and runs its own `enroot start` there, so `--env` applies on that node:

```bash
MODEL=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/qwen3/models/Qwen3-0.6B
NODES=($(sort -u "${PBS_NODEFILE}"))
HEAD=${NODES[0]}; TAIL=${NODES[1]}
HEAD_IP=$(getent ahostsv4 "${HEAD}" | awk '{print $1; exit}')
TAIL_IP=$(getent ahostsv4 "${TAIL}" | awk '{print $1; exit}')
IB=mlx5_0:1,mlx5_3:1,mlx5_4:1,mlx5_5:1,mlx5_6:1,mlx5_9:1,mlx5_10:1,mlx5_11:1

worker() {   # worker <node> <role> <port> [extra sglang flags]
  local node=$1 role=$2 port=$3; shift 3
  ssh "${node}" "export PBS_JOBID=${PBS_JOBID}; \
    enroot start --env UCX_NET_DEVICES=${IB} sglang \
      python3 -m sglang.launch_server --model-path ${MODEL} --served-model-name qwen \
        --trust-remote-code --context-length 4096 --tp-size 1 --mem-fraction-static 0.4 \
        --disaggregation-mode ${role} --disaggregation-transfer-backend nixl \
        $* --host 0.0.0.0 --port ${port}"
}
worker "${HEAD}" prefill 30100 --disaggregation-bootstrap-port 9000 > prefill.log 2>&1 &
worker "${TAIL}" decode  30200 --max-running-requests 256           > decode.log  2>&1 &
# wait for http://${HEAD_IP}:30100/health and http://${TAIL_IP}:30200/health

enroot start sglang python3 -m sglang_router.launch_router --pd-disaggregation \
  --prefill "http://${HEAD_IP}:30100" 9000 --decode "http://${TAIL_IP}:30200" \
  --host 0.0.0.0 --port 8000 > router.log 2>&1 &
# wait for http://${HEAD_IP}:8000/health, then AIPerf against 127.0.0.1:8000 as in Step 3
```

`UCX_NET_DEVICES` lists the eight compute HCAs; the prefill log shows `NIXL KVManager initialized with backend: UCX`.

Two things to handle at the end of the job:

- Processes started over ssh are not children of your job script. Stop them explicitly (for example `ssh <node> "pkill -u $(id -u) -f 'sglang[.]launch_server'"`) before the script exits.
- The SGLang router does not exit promptly on SIGTERM, so a `wait` on it at the end of the script can hold the job until its walltime runs out. Kill it and don't wait.

## Fitting Qwen3-235B FP8 on H100

The FP8 weights are 236 GB. On an 80 GB H100 a worker needs at least four GPUs (320 GB): the `3.1-firmus-scripts/07` topology, with prefill workers at TP=2, runs out of memory while loading weights here (2 × 80 GB = 160 GB). It fits on Firmus only because an H200 has 141 GB. With 16 H100s you have at most four TP=4 workers, or fewer, wider ones.

## A 16-GPU reference deployment of Qwen3-235B

This is the `3.1-firmus-scripts/09` topology (here `09-pd-235b-fatp.pbs`), which fits on H100: **2 prefill workers at TP=4** on node 0 and **2 decode workers at TP=4, EP=4** on node 1, router on node 0. The worker flags are 09's (and the same as 3.1's common flags); only the launch differs.

```bash
#PBS -l select=2:ncpus=112:ngpus=8:mpiprocs=1:mem=1880gb:container_engine=enroot
#PBS -l place=scatter:excl
#PBS -l container_image=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/qwen3/images/sglang-v0.5.17-cu129.sqsh
#PBS -l container_name=sglang
#PBS -l walltime=00:19:30
```

Each worker, started over ssh on its node as in the two-node example:

```bash
enroot start \
  --env CUDA_VISIBLE_DEVICES=${gpus} \
  --env UCX_NET_DEVICES=${IB} \
  --env UCX_POSIX_USE_PROC_LINK=n \
  --env TRITON_CACHE_DIR=/tmp/sglang-${name}/triton \
  --env TORCHINDUCTOR_CACHE_DIR=/tmp/sglang-${name}/inductor \
  --env TMPDIR=/tmp \
  sglang python3 -m sglang.launch_server \
    --model-path ${MODEL} --served-model-name qwen --trust-remote-code \
    --context-length 8192 --tp-size 4 --mem-fraction-static 0.90 \
    --disaggregation-mode ${role} --disaggregation-transfer-backend nixl \
    ${extra} --host 0.0.0.0 --port ${port}
```

| Worker | Node | GPUs | Port | Extra flags |
|---|---|---|---|---|
| prefill-0 | 0 | 0,1,2,3 | 30100 | `--disaggregation-bootstrap-port 9000` |
| prefill-1 | 0 | 4,5,6,7 | 30101 | `--disaggregation-bootstrap-port 9001` |
| decode-0 | 1 | 0,1,2,3 | 30200 | `--ep-size 4 --max-running-requests 256` |
| decode-1 | 1 | 4,5,6,7 | 30201 | `--ep-size 4 --max-running-requests 256` |

The router on node 0 lists both prefill workers (with their bootstrap ports) and both decode workers, and listens on port 8000, as in 3.1.

Besides the flags, three things are needed:

- **Read the weights once per node before starting the workers.** Four workers loading 236 GB each straight from `/scratch` took 4.5–11 minutes. Reading the safetensors files first with parallel sequential streams took 10–11 seconds per node, after which the workers loaded in 43–141 seconds:

  ```bash
  ssh <node> "find ${MODEL} -name '*.safetensors' | xargs -P 24 -I{} dd if={} of=/dev/null bs=16M status=none"
  ```

- **Set `TMPDIR=/tmp` for the workers.** PyTorch's symmetric memory creates a socket under `$TMPDIR`, and the job's `TMPDIR` (`/raid/pbs.<job-id>` on the host) does not exist inside the container. Without it the log shows `Setup Custom allreduce failed with Failed to bind socket` and SGLang falls back from its custom all-reduce.
- **Give the AIPerf container the HTTPS proxy.** The official command loads the tokenizer by its Hugging Face name, and the proxy variables of the job environment are not passed into containers. A file in `~/.config/enroot/environ.d/` is read for every container you start. Generate it once from the job environment, in any job script:

  ```bash
  mkdir -p ~/.config/enroot/environ.d
  env | grep -iE '^(https_proxy|no_proxy)=' | tr -d '"' > ~/.config/enroot/environ.d/50-https-proxy.env
  ```

  `tr -d '"'` removes the quotes the site puts around the `no_proxy` value. Only the HTTPS proxy is copied, so the plain-HTTP traffic between router and workers is untouched. At the time of writing the file comes out as:

  ```bash
  no_proxy=nscc.sg,.nscc.sg,asp2p.nscc.sg,.asp2p.nscc.sg,a2ap-bcm01,a2ap-bcm02,a2ap-access01,a2ap-access02,localhost,127.0.0.1,10.104.0.0/21
  https_proxy=http://10.104.4.124:10104
  NO_PROXY=NSCC.SG,.NSCC.SG,ASP2P.NSCC.SG,.ASP2P.NSCC.SG,LOCALHOST,A2AP-BCM01,A2AP-BCM02,A2AP-ACCESS01,A2AP-ACCESS02,127.0.0.1,10.104.0.0/21
  HTTPS_PROXY=http://10.104.4.124:10104
  ```

  Without this file the tokenizer step stalled for about nine minutes.

The first job also spends several minutes compiling DeepGEMM kernels; they are cached in `~/.cache/deep_gemm`, and later jobs start in under 5 minutes.

The official command then runs through the router, inside the AIPerf container, as one string; `official-aiperf.sh` is in [3.2-aspire2p-scripts/](3.2-aspire2p-scripts/):

```bash
enroot start aiperf "cd ${ART} && N=${N} HOST=127.0.0.1:8000 MODEL=qwen bash official-aiperf.sh"
```

### Results

Same deployment, same two nodes, one job per concurrency, official command unmodified. "Good output tok/s" is output token throughput × `good_request_fraction` (every request has 200 output tokens).

| N | `good_request_fraction` | Good output tok/s | Output tok/s | TTFT avg / p90 (ms) | ITL avg / p90 (ms) | Requests | PBS job |
|---:|---:|---:|---:|---:|---:|---:|---|
| 24 | **0.986** | 1,054 | 1,068 | 872 / 1,396 | 17.84 / 18.84 | 659 | 217990.pbs111 |
| 32 | **0.908** | 1,174 | 1,292 | 1,150 / 1,879 | 18.86 / 19.94 | 797 | 217989.pbs111 |
| 48 | 0.309 | 508 | 1,644 | 1,698 / 2,667 | 20.20 / 21.13 | 1,033 | 217819.pbs111 |
| 64 | 0.081 | 155 | 1,910 | 2,344 / 3,364 | 21.10 / 21.81 | 1,208 | 217834.pbs111 |

With this split on H100, decode ITL crosses 20 ms between N=32 and N=48, so the gate fails there even though TTFT stays under 3 s. N=32 clears the gate with little margin. These numbers are a starting point for this one split, not a target; raw throughput is not compared across platforms.

Each job took about 8.5 minutes of walltime (about 4.5–5 minutes to READY, then AIPerf), about 290 SU.
