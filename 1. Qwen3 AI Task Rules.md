# Qwen3-235B-A22B PD Disaggregated Inference Task

## Task Workload and Input

Participants are required to optimize the following workload for improved throughput.

- Framework/deployment: disaggregated Prefill/Decode (PD) inference serving. No specific stack is mandated (SGLang or any other compatible stack is acceptable).
- Model: [`Qwen3-235B-A22B-Instruct-2507`](https://huggingface.co/Qwen/Qwen3-235B-A22B-Instruct-2507) (MoE). Weight precision must be FP8.
- Input dataset: synthetic data generated by AIPerf (Shakespeare-corpus text slices).
  - Input sequence length (ISL): **4000** tokens (stddev = 0)
  - Output sequence length (OSL): **200** tokens (stddev = 0)
- Performance metric: output token/s of **good requests** (requests that pass the SLA gate defined in Task Rules).
- Node limit: this task can be optimized on either of two provided platforms (see Cluster Usage below):
  - **Firmus AI Cloud cluster**: 2× HGX H200 nodes (**16 GPUs** total), interconnected by **8× InfiniBand NDR**.
  - **NSCC Singapore ASPIRE 2A+**: 2× HGX H100 nodes (**16 GPUs** total).
- Time limit: `--benchmark-duration 120` seconds, plus a non-scored `--warmup-duration 60` seconds and a trailing `--benchmark-grace-period 30` seconds.

## Task Rules

- A request counts as **good** only if it simultaneously satisfies TTFT ≤ 3000ms and average ITL ≤ 20ms. Errors count toward the denominator of `good_request_fraction`. The threshold is `good_request_fraction ≥ 0.90`. A declared point that does not clear this threshold is not scored.
- Prefill and Decode **must** be deployed disaggregated (PD disaggregation). Colocated deployment is prohibited. The P/D split ratio is free to choose, but the scored run must use all 16 GPUs provided on the chosen platform.
- KV cache defaults to FP8. Engines that only support BF16 KV cache may still compete under the same thresholds and scoring. No compensation is given for this limitation.
- The official benchmark run only accesses each team's exposed OpenAI-compatible gateway at `/v1/chat/completions`. Pointing the benchmark directly at a Prefill or Decode worker's internal address is prohibited.
- The official evaluation command is fixed and must not be modified **for the official scored re-run**.
- This restriction applies only to that one official re-run. During your own local testing, parameter sweeps (e.g., trying different TP/PP/EP/DP degrees or Prefill:Decode worker ratios), or when generating supporting performance data for the presentation, you may run AIPerf with any duration, warmup, seed, cache-bust setting, or other value that helps you iterate quickly. These exploratory runs carry no scoring weight and are not checked against the locked command below. You do not need the full 120-second `--benchmark-duration` to tell two configurations apart. A much shorter duration, 10 to 20 seconds for example, is usually enough to see the relative difference while sweeping. Save the full-length official duration for the one official re-run.

```bash
N=<team-declared concurrency>
HOST=<gateway host:port>
MODEL=<team's /v1/models id>   # tokenizer remains Instruct-2507, so the 4000-token measurement stays on one common ruler

aiperf profile \
  --url "http://${HOST}" \
  --endpoint-type chat \
  --endpoint /v1/chat/completions \
  --model "${MODEL}" \
  --tokenizer Qwen/Qwen3-235B-A22B-Instruct-2507 \
  --streaming \
  -H 'Accept: text/event-stream' \
  --concurrency "${N}" \
  --workers-max "${N}" \
  --api-key NOT_USED \
  --warmup-duration 60 \
  --benchmark-duration 120 \
  --benchmark-grace-period 30 \
  --synthetic-input-tokens-mean 4000 \
  --synthetic-input-tokens-stddev 0 \
  --output-tokens-mean 200 \
  --output-tokens-stddev 0 \
  --extra-inputs min_tokens:200 \
  --extra-inputs max_tokens:200 \
  --extra-inputs ignore_eos:true \
  --extra-inputs temperature:0.0 \
  --extra-inputs repetition_penalty:1.0 \
  --num-dataset-entries 12800 \
  --random-seed 2026 \
  --cache-bust first_turn_prefix \
  --goodput "time_to_first_token:3000 inter_token_latency:20" \
  --ui simple
```

- This is a **closed-loop** benchmark: the declared concurrency N is sustained by immediately issuing a new request as soon as one completes. Substituting `--request-rate` (or any other open-loop / Poisson-arrival pattern) for closed-loop is prohibited. Scores obtained with a self-added rate flag are invalid.

## General Rules

### Cluster Usage

This task can be optimized on either of two provided platforms:

- **Firmus AI Cloud cluster**: 2× HGX H200 nodes, 16 GPUs total, interconnected by InfiniBand NDR.
- **NSCC Singapore ASPIRE 2A+**: 2× HGX H100 nodes, 16 GPUs total.

Teams choose which platform to optimize on, and may present optimization work done on other GPU clusters as supplementary information. If one platform is unavailable due to maintenance, teams may switch to the other to continue their work without disruption to the competition schedule.

### Evaluation Criteria

Beyond the throughput score, submissions are also assessed on:

- **Technical evaluation**: whether the team's optimization approach is clearly and correctly explained.
- **Innovation evaluation**: whether the submission demonstrates novel optimization ideas.

These criteria are evaluated primarily through each team's presentation. Detailed presentation requirements and scoring are covered separately, below.

### Performance Assessment

Cross-team performance comparison is based on **good** output token/s (i.e., throughput measured only from requests that pass the SLA gate defined in Task Rules). Because the Firmus AI Cloud cluster and NSCC Singapore ASPIRE 2A+ use different GPU generations, raw throughput is not directly compared across platforms. It is one factor the judges weigh alongside optimization methodology and technical understanding (see Evaluation Criteria and Scoring). A declared concurrency point that does not clear the `good_request_fraction ≥ 0.90` threshold does not participate in the performance ranking comparison.

## Optimization Guidelines

### Allowed

- Choice of serving stack/framework.
- Parallelism strategy (e.g., TP/PP/EP/DP).
- Prefill/Decode split ratio and routing.
- Scheduling.
- Compute and communication optimization (e.g., kernel/CUDA graph tuning, NCCL/IB tuning, overlapping compute with communication, reducing cross-node KV transfer latency).

This list is not exhaustive. If you are unsure whether an optimization idea is allowed, ask in the team Slack channel (see Technical Support below). Confirmed additions will be added to this list.

### Prohibited

- Modifying the benchmark client, the benchmark dataset, the official AIPerf command, or the random seed **for the official scored re-run** (see Task Rules above for what applies to a team's own exploratory testing).
- Substituting `--request-rate` (or any other open-loop pattern) for the required closed-loop benchmarking mode.
- Bypassing the gateway endpoint to send benchmark traffic directly to a Prefill or Decode worker.
- Using model weights that are not FP8.
- Reporting a score when the context window cannot fully accommodate the official request (template + 4000 input tokens + 200 output tokens).

### Additional Restrictions

An invalid P/D split, slow cross-node tensor parallelism, or a KV cache engine limited to BF16 are treated as a team's own implementation limitation. These are not rule violations, and no compensation or score adjustment is given for them.

## Recommendations

### Optimization Methodology

- Before spending cluster time on the full 235B model, use a small model (e.g., Qwen 0.6B, or a small MoE such as Qwen 1.5B) to smoke-test whether a deployment topology or configuration combination runs correctly at all. This is fast enough to sanity-check most combinations. It does not predict performance, since the compute/communication balance and memory pressure at 235B scale are different, so any actual tuning decision still has to be made on the real model.
- Profile the serving stack first to identify the actual bottleneck (prefill compute, decode latency, KV cache transfer, network, scheduling, etc.) before making changes.
- Based on the profiling results, iteratively adjust the TP/PP/EP/DP degrees, the Prefill:Decode worker ratio, and other parallelism choices to target the identified bottleneck.
- Systematically log every attempt (configuration, parameters, and resulting throughput/goodput), so that the improvement path can be reproduced and clearly presented afterward.
- During iteration, use a much shorter benchmark duration than the official 120 seconds. A short run is normally enough to tell whether a change helped, and it lets you test more configurations within your allotted cluster time. Reserve the full official duration for confirming your final configuration before the official re-run.

### Presentation Excellence

- Clearly narrate the problem-solving path: what bottleneck was found, why it mattered, and how each optimization step addressed it.
- Quantify the improvement achieved at each step (e.g., before/after throughput, before/after `good_request_fraction`), rather than describing changes only qualitatively.
- Demonstrate technical depth by explaining the reasoning behind each design choice, not just the final configuration.

### Q1. Basic (vanilla)

Model and precision:

- Serve `Qwen3-235B-A22B-Instruct-2507-FP8` as published. Do not distil, requantise, prune, merge, skip layers or experts, or replace it.
- Weights in FP8. KV cache in FP8 (default) or higher (BF16, FP16). KV storage and cross-node KV transfer below FP8 are not allowed. This includes INT8, INT4, and FP4.

Speculative decoding (lossless only):

- Allowed when the target model verifies every token, so that under the official greedy settings the output tokens are the same as the target model alone.
- The draft may be an EAGLE-3 head, an MTP head, or a small draft model. It may be public, or trained or fine-tuned by your team.
- A draft you train or fine-tune must not target this task's data or workload. Do not train it on the Shakespeare corpus that AIPerf uses, on requests generated by AIPerf, or on the target model's answers to such prompts. General-purpose training data is fine.
- If you train or fine-tune a draft, publish the training method in your result package: data, scripts, and settings, enough for the judges to check the rule above.
- Draft weights may be FP8 or higher precision, including BF16 weights quantised to FP8 at load time.
- Declare every draft in your result package: where it came from (link, or "trained by the team"), its size, and its precision.

Serving stack and topology:

- Any serving stack. You may configure it and patch it, as long as the patches do not change what the model computes. Submit patches as text; the judges review them.
- The textbook split (prefill workers and decode workers) is the Basic baseline. Finer splits, for example at attention, are allowed if they serve the official requests on the same 16 GPUs under the same SLAs.
- In Basic, every request is prefilled on a prefill worker and decoded on a decode worker. Sending a request's prefill to a decode worker (for example when prefill workers are full) is colocated serving for that request. It is not Basic. You may present it as Bonus work (Q2); the Basic submission that the organisers re-run must be plain PD.

Benchmark client and warm-up:

- The AIPerf client needs no GPU. You may run it on a login node. The intended placement is the same two-node allocation. Do not add a third compute node.
- Do not change the AIPerf protocol (warm-up, drain, window, SLAs, cache-bust, seed).
- Engine, compiler, and CUDA-graph warm-up before the official command are allowed.
- A few connection warm-up requests to your gateway before the official command are allowed, inside the same job script. Their purpose is to set up the KV-transfer path on every prefill–decode pair; on a cold PD layout the first request on a pair can otherwise stall for minutes. Do not use the official benchmark dataset or seed for them. The official `--warmup-duration 60` is not changed and still runs.

Output quality:

- The organisers run a full-set accuracy check. The pass line is 99% of the reference score.
- The reference score is the organisers' own run of the official FP8 checkpoint, served without changes, on the same checks. It is not the numbers printed on the model card: those are for the BF16 original.
- The checks include, but are not limited to, benchmarks listed on the model's Hugging Face model card and AIPerf's checks.
- A mathematically exact implementation passes. The check exists to catch serving that is "dumbed down".

Official re-run:

- The organisers rebuild your stack from your build instructions under a dedicated account, not your team's account, and run the official command against your gateway.
- The metric is good output token/s = `goodput` (req/s) × 200, read from `profile_export_aiperf.json`.

### Q2. Bonus: experimental work

- Careful Basic tuning can earn Bonus points on its own (README Addendum R2).
- Experimental work is anything outside Basic that still computes the same model output: for example new serving-stack mechanisms, scheduling schemes, or custom kernels that Basic does not cover.
- Self-proof: pass the accuracy check in Q1, explain why the output is unchanged, and submit the patches and deployment method so the judges can review them.
- Measure the speedup against your own Basic result on the same platform.

"The benefit outweighs the quality loss" is not a Bonus argument. A technique that loses quality changes the math. It is Prohibited (Q3).

### Q3. Prohibited in every tier

In addition to the Prohibited list above:

- Any technique that skips or approximates computation of the model on the official request: prompt pruning, token dropping, sparse or approximate prefill that does not attend to all 4000 input tokens, KV eviction, layer or expert skipping.
- Precision below FP8 anywhere in the served path (weights, activations, KV storage, KV transfer).
- Serving a different or smaller model in place of the required checkpoint.

### Q4. Short answers

These apply to every team.

- **Is PD disaggregation required?** Yes. Colocated serving is not Basic (Q1).
- **May the KV cache be stored or sent in 8-bit or 4-bit?** FP8 yes; it is the default. INT8, INT4, and FP4 no. INT8 is also 8 bits, but it is a different format and below FP8 (Q1, Q3). BF16 is fine.
- **Must methods be mathematically lossless?** They must not change what the model computes. Different kernels and serving stacks order floating-point operations differently; that is fine. Approximations that skip or drop work are not (Q1, Q3).
- **How is output quality checked?** A full-set accuracy check on benchmark tasks. It compares benchmark scores, not logits. The reference is the organisers' run of the official FP8 checkpoint, served without changes. The pass line is 99% of the reference score (Q1).
- **SGLang and vLLM give slightly different outputs. Is that a problem?** Not by itself. The check compares benchmark scores against the reference, not the output token by token.
- **Basic: is "FP8 or higher everywhere, and lossless methods" enough?** Yes, within the rest of Task Rules and Q1.
- **Bonus: is a lossy technique allowed if the speedup outweighs the quality loss?** No. Bonus work must still compute the same model output (Q2).
