# OpenFOAM Application Notes: ASPIRE-2A

These are the organisers' vanilla reference runs on **NSCC ASPIRE-2A**, and how to set yourself up there. The Gadi counterpart is [4.2 OpenFOAM Application Notes - Gadi.md](4.2%20OpenFOAM%20Application%20Notes%20-%20Gadi.md). Numbers from the two machines are not directly compared (Task Rules, "Performance Assessment").

This is not an Allrun tutorial; for that, see [4.1 OpenFOAM Application Notes - Iris.md](4.1%20OpenFOAM%20Application%20Notes%20-%20Iris.md).

## Setting up on ASPIRE-2A

### Disk

```bash
myquota        # home 50 GB; scratch 100 TB and 200 million inodes
myprojects     # your project's SU balance
```

| Directory | What it is |
|---|---|
| `~/scratch` → `/scratch/users/<organisation>/<…>/<user>` | Your Lustre scratch. The run directories below were all here. |
| `/home/project/<project>` | The project's shared directory: NFS, `drwxrws---`, group `<project>`. Personal home and scratch directories belong to each user's private group. |

What one run needs:

| Item | Size |
|---|---:|
| `polyMesh_65M.tar.gz` | 3.2 GB |
| Unpacked `polyMesh` | 7.0 GB |
| One run directory after the full chain (`processor*`, 128 / 256 / 512 ranks) | about 10 GB |

### Getting the mesh

A copy of the official Zenodo tarball is on ASPIRE-2A for every user:

```
/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/openfoam/polyMesh_65M.tar.gz
/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/openfoam/polyMesh_65M.tar.gz.md5
```

The parent directory cannot be listed; use the full path.

```bash
P=/scratch/users/industry/hpcadvisorycouncil/pengzhi/public/2026-apac-hpc-ai/openfoam
mkdir -p ~/scratch/occDrivAer/mesh
cd ~/scratch/occDrivAer/mesh
cp $P/polyMesh_65M.tar.gz* .
md5sum -c polyMesh_65M.tar.gz.md5      # polyMesh_65M.tar.gz: OK
tar -xzf polyMesh_65M.tar.gz           # gives polyMesh/
```

The copy took 6 s and the unpack 61 s.

If the shared copy is not readable, download from Zenodo (reachable from the login nodes) and check the same md5:

```bash
wget -O polyMesh_65M.tar.gz "https://zenodo.org/records/15012221/files/polyMesh_65M.tar.gz?download=1"
echo "50393a15d84f53255fda85ac702390e9  polyMesh_65M.tar.gz" | md5sum -c
```

The unpacked mesh has 65 334 765 cells (`grep -a nCells polyMesh/owner`). Many case directories can link one unpacked `polyMesh` (`ln -s <path>/polyMesh constant/polyMesh`); all the runs below did this.

## How the reference runs were made

| | |
|---|---|
| Nodes | standard CPU nodes: AMD EPYC 7713, 128 cores, 440 GiB per node |
| OpenFOAM | site module `openfoam/2512` (cray-mpich 8.1.15); logs show `Build : _87ed40d256-20251219 OPENFOAM=2512 version=v2512`, the same build as the Gadi module |
| Case | official [occDrivAerStaticMesh](https://develop.openfoam.com/committees/hpc/-/tree/develop/incompressible/simpleFoam/occDrivAerStaticMesh) at commit `84c26243`, `fvSolution.fixedIter`, `controlDict.noWrite` |
| Mesh | Zenodo 15012221 `polyMesh_65M.tar.gz` |
| Ranks | full nodes: 128 / 256 / 512 MPI ranks, `mpirun -np <N>` with no extra options |
| `endTime` | 40 / 80 / 150 on 1 / 2 / 4 nodes |
| Changed | only `system/include/caseDefinition`: `nCores`, `decompositionMethod`, and `nHierarchical` for `hierarchical` |

Decomposition:

- `hierarchical`: `nHierarchical` `(16 4 2)` / `(16 8 2)` / `(16 8 4)`. `(16 8 4)` is the case's own; the other two are simple factorisations, not tuned.
- `scotch`: no `scotchCoeffs`, so Scotch's own defaults.

### PBS

```bash
#PBS -P <project>
#PBS -q normal
#PBS -l select=4:ncpus=128:mpiprocs=128:mem=440gb
#PBS -l place=excl
#PBS -l walltime=00:40:00
#PBS -j oe

module load openfoam/2512
```

- `-q normal` is a routing queue; execution queues refuse direct submission.
- Without `mem=` a job gets 10 MB.
- Nodes are shared by default; `place=excl` keeps other jobs off them.
- Routing from `normal`, as seen for these jobs: up to 128 cores with walltime up to 2 h goes to `qdev`, which has a limit of 256 cores in use across all users; 1 node with walltime over 2 h goes to `q4`; 129–2048 cores go to `q5`. The 1-node reference runs asked for `walltime=02:00:01` and ran in `q4`. The 4-node runs first asked for `walltime=01:00:00` and did not start in five hours; the same jobs asking for `00:40:00` (`00:20:00` for `simpleFoam` only) started within 35 minutes. Billing uses the walltime used, not the walltime requested (see [What one run costs](#what-one-run-costs)).

### The commands

The runs executed Allrun's commands one by one, with Allrun's flags, instead of calling `Allrun`:

```bash
cp system/controlDict.noWrite system/controlDict
cp system/fvSolution.fixedIter system/fvSolution
mkdir logFiles
decomposePar -constant > logFiles/10_decomposePar.log 2>&1
. $WM_PROJECT_DIR/bin/tools/RunFunctions; restore0Dir -processor
mpirun -np $N renumberMesh -constant -overwrite -parallel > logFiles/20_renumberMesh.log 2>&1
mpirun -np $N potentialFoam -initialiseUBCs -parallel     > logFiles/30_potentialFoam.log 2>&1
mpirun -np $N applyBoundaryLayer -ybl 0.0450244 -parallel > logFiles/40_applyBoundaryLayer.log 2>&1
mpirun -np $N simpleFoam -parallel                        > logFiles/50_simpleFoam.<timestamp>.log 2>&1
```

Each step was judged by the line `End` in its log, not by its exit code. On 2 and 4 nodes every parallel step printed `End`, then one rank died with signal 7 (SIGBUS) while MPI shut down, and `mpirun` returned 135 or 143. From `scotch-2node/20_renumberMesh.log`:

```
End

Finalising parallel run
x1003c3s1b0n1.hostmgmt2003.cm.asp2a.nscc.sg: rank 106 died from signal 7
```

The results (fields, `coefficient.dat`, the Average line) are all written before this. Allrun ends each step with `|| exit 1`, so run unchanged it stops after the first parallel step on more than one node. On 1 node no step returned non-zero.

### Where the signal 7 comes from

It does not need OpenFOAM. Between nodes the module's MPI uses `verbs;ofi_rxm` on the `mlx5` adapters with XRC: `MPICH_OFI_VERBOSE=1` prints `MPICH CH4 OFI netmod using verbs;ofi_rxm provider (domain_name=mlx5_0-xrc)`, and `MPICH_ENV_DISPLAY=1` shows `FI_VERBS_PREFER_XRC = 1` and `FI_OFI_RXM_USE_SRX = 1`.

A short C program ([`a2a.c`](4.3-aspire2a-logs/sigbus-probe/a2a.c)) does one `MPI_Alltoall`, an `MPI_Barrier`, then `MPI_Finalize`, and prints a line from every rank before and after `MPI_Finalize`. Built with `cc` under `module load openfoam/2512`, run with `mpirun -np 256` on 2 nodes:

| Setting | Runs with signal 7 | Ranks returning from `MPI_Finalize` |
|---|---:|---:|
| defaults, 16 KiB per rank pair | 3 of 3 | 0 of 256 |
| defaults, 1 KiB per rank pair | 3 of 3 | 0 of 256 |
| `FI_OFI_RXM_BUFFER_SIZE=65536` | 3 of 3 | 0 of 256 |
| `FI_VERBS_PREFER_XRC=0` | 0 of 3 | 256 of 256 |
| `FI_OFI_RXM_USE_SRX=0` | 0 of 3 | 256 of 256 |

Also measured, all with the signal 7 still there:

- `FI_MR_CACHE_MONITOR=memhooks`, `userfaultfd` or `disabled`, and `FI_MR_CACHE_MAX_COUNT=0`: 3 of 3 each ([`stage.c`](4.3-aspire2a-logs/sigbus-probe/stage.c), an `MPI_Allreduce` followed by the same `MPI_Alltoall`).
- `MPICH_SMP_SINGLE_COPY_MODE=CMA`. The compute nodes have no `/dev/xpmem`, so CMA is already what the defaults use.
- `MPIR_CVAR_NO_COLLECTIVE_FINALIZE=1`, with `simpleFoam`.

The same programs exited cleanly with only `MPI_Init` and `MPI_Finalize`, with only an 8-byte `MPI_Allreduce`, and on 1 node.

With OpenFOAM, `simpleFoam` for 3 steps on 2 nodes, reusing the `scotch` 256-rank decomposition:

|---|---|---:|---|
| defaults | 25710451 | 135, signal 7 after `End` | 0.39429246700596987 |

### What Cd tells you

- These Cd values are for 128 / 256 / 512 ranks. Gadi's are for 104 / 208 / 416 ranks, a different decomposition, so they differ.
- Cd depends on the decomposition. `hierarchical` and `scotch` differ from each other by 0.7% at 40 steps, 3.0% at 80 steps and 3.5% at 150 steps.
- With `scotch`, the split and `simpleFoam`-only runs below reproduced the one-job run exactly: the whole `coefficient.dat` (every step, every column) is identical at 1, 2 and 4 nodes. `hierarchical` was not repeated.
- How Cd is checked is in the Task Rules ("Sanity check", Addendum F0 and F3).

## What one run costs

ASPIRE-2A charges 1 SU per core-hour, on the cores requested (`ncpus`) times the walltime used. `place=excl` does not change this: a 16-core `place=excl` job and a 16-core shared job, each sleeping 5 minutes, were both billed for 16 cores. The project's usage over the first 13 jobs (the two 16-core tests, the 1- and 2-node runs, and the 1- and 2-node split and reuse runs) went up by 327.516 core-hours, the same as the sum of `ncpus × walltime used` over those jobs to three decimals. For the whole day, `myprojects -l` reports 904.66 SU against 895.27 SU summed over the 19 jobs in this note; the 9.39 SU difference was not traced to a job.

Use `qstat -fx <jobid>` after a job ends to see `resources_used.walltime` and `ncpus`. `myprojects` and `myusage` are updated from snapshots, not per job.

## Splitting the chain into two jobs

`decomposePar` is a single process, but a one-job run holds every requested core while it runs. Addendum F1 allows splitting the chain across separate jobs, as long as every step still runs:

1. **Serial job**, 16 cores, `mem=64gb`, without `place=excl`: the two `cp`, `decomposePar -constant`, `restore0Dir -processor`.
2. **Parallel job**, full nodes, `place=excl`, started only if the first one succeeded: `renumberMesh`, `potentialFoam`, `applyBoundaryLayer`, `simpleFoam`.

```bash
a=$(qsub -l select=1:ncpus=16:mem=64gb serial.pbs)
qsub -W depend=afterok:$a -l select=4:ncpus=128:mpiprocs=128:mem=440gb -l place=excl parallel.pbs
```

The 16-core jobs ran in `qdev`.

What it saved with `scotch` (same case, same mesh, same module):

| Nodes | One job | Serial job | Parallel job | Split total | Saved |
|---:|---:|---:|---:|---:|---:|
| 1 | 33.60 SU | 1.33 SU (00:04:59) | 27.95 SU (00:13:06) | 29.28 SU | 13% |
| 2 | 74.88 SU | 1.61 SU (00:06:03) | 53.48 SU (00:12:32) | 55.09 SU | 26% |
| 4 | 149.62 SU | 2.24 SU (00:08:24) | 80.50 SU (00:09:26) | 82.74 SU | 45% |

A full 1 / 2 / 4-node `scotch` set drops from 258 SU to 167 SU. The split runs gave the same `coefficient.dat` as the one-job runs. Splitting changes SU and walltime, not Average.
